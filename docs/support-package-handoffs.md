# Support request package handoffs

`SupportPackageHandoff` is immutable lineage between an exact tenant-and-venue-scoped support request version and an already-existing `DRAFT` venue package.

Only a human platform support operator can create a link. The canonical domain action rejects closed requests, stale request versions, cross-scope records, non-draft packages, duplicate links, and client actors. The request version increment, relation insert, support audit event, and strict global audit record share one transaction.

The action never creates a package and never approves, applies, reverts, publishes, or otherwise changes package lifecycle state. The Internal Support UI deliberately exposes only an existing-draft selector and historical lineage. The migration is forward-only and must be reviewed and applied through the normal database release process; it is not applied by this implementation.

The package review screen now carries the latest exact support-request handoff, effective change preview, and package-bound evaluation history together. An error-free `DRAFT` or `APPROVED` package can prepare the seven-dimension onboarding suite and freeze a `REVIEWABLE_VENUE_PACKAGE_V1` evaluation target. This is review evidence only: it does not approve, apply, publish, message a customer, enable a provider, or define a release threshold. Package lifecycle controls remain separate, and the UI reports quality outcomes separately from operational failures.

The machine-operable approval bridge preserves that separation. An authorized worker may prepare an exact package-approval proposal after review evidence exists. The founder decision produces only one-shot `DRAFT`-to-`APPROVED` authority; a later agent call must consume it against the unchanged package and handoff. The human decision-maker remains the package approver while the mechanical agent execution receives its own run/action/grant lineage. No evaluation threshold is implied, and application, publication, reversion, support mutation, and customer contact remain outside this authority.

The application bridge is separately gated. A verified `packages:apply` worker may freeze the exact unchanged `APPROVED` package for founder review, but neither proposal nor decision changes content. The review surface explicitly warns that execution mutates current venue content and may be visitor-visible. The separate executor consumes one exact founder-issued grant and uses the canonical package application lifecycle with agent/run/worker/credential/grant lineage. It does not complete the support request, message or contact the customer, trigger external delivery, or revert the package. Replay converges on the original applied package; drift fails closed.

The recovery bridge is independently gated. A verified `packages:revert` worker may freeze one exact unchanged `APPLIED` package, rollback-manifest digest, handoff, and active support-request version for founder review. `COMPLETED` support requests are deliberately ineligible, preventing rollback from silently invalidating recorded fulfillment. The founder decision issues one-shot authority but changes nothing. The executor consumes that exact grant and calls the canonical package rollback, retaining its existing content-drift and recoverability checks. It cannot change support state, contact a customer, deliver externally, or establish an automatic rollback policy. Exact replay converges; package, manifest, handoff, request, or parameter drift fails closed.

Support completion now closes the lifecycle without collapsing those authorities. For a package-backed request, the completion proposal is unavailable until every linked package is fully `APPLIED`. It freezes each handoff, package ID, handoff request version, payload hash, application timestamp, application actor/command, package update timestamp, and a deterministic digest. Founder approval issues completion authority for only that exact fulfillment state. The later completion transaction recomputes and compares it before creating the one reviewed in-app client-visible message and moving the request to `COMPLETED`. Package-free support requests remain eligible, while a draft, approved, reverted, incomplete, newly linked, or otherwise changed package fails closed. The canonical manual completion path shares the same current-state guard.

## Support status transitions

Support status changes use a separate human-operator-only domain action with exact scope, request-version CAS, an append-only `STATUS_CHANGED` support event, and strict platform audit in the same transaction. The graph is deliberately closed: received requests may wait for client information or enter review; review may return for information or record a package draft; package drafts move through validation, approval waiting, applying, and completion. Cancellation is allowed before applying. Terminal requests cannot reopen.

`VALIDATING` is the existing support-request enum's closest lifecycle stage for validation and evaluation review; no separate support-request evaluation status exists. The evaluation run has its own durable lifecycle and exact package identity, while the support status remains an operator-controlled evidence label. Neither changes package lifecycle state. Client APIs continue to expose status as read-only data and provide no transition procedure.
