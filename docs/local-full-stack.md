# Local full stack design (Packet 14, M1)

Status: M1 reviewed before implementation on 2026-09-28. Sol self-reviewed the note, then two independent Luna cold reviews found egress, bind, alias, cookie and bundle-scan gaps; this version incorporates those findings. Base: R1.1 `512df5d4329ac4842b1c5e3cb9ea6cd92710d324`.

## Authentication seam

Use a **development-only webpack module alias in each Next app** for the Clerk browser and server entry points. The launcher runs the installed Next 15 `next dev` on exact loopback ports (webpack is its default and this CLI has no `--webpack` switch), and config-time refusal tests admit only that exact parent command or Next 15's internal `start-server.js` child with `NEXT_PRIVATE_WORKER=1`; the preloaded listener guard forbids a non-loopback TCP bind in either process. Live browser sign-in, middleware, server-component and tRPC checks establish that the alias resolved on the relevant paths. The normal source imports stay intact. The alias maps both exact specifiers, `@clerk/nextjs` and `@clerk/nextjs/server`, to small harness modules only when `TORCHIKO_LOCAL_FIXTURE_AUTH=1` and `NODE_ENV=development`; ordinary dev and all production builds resolve the real package. Resolution must be proven separately for browser, server components, route handlers, middleware and workspace imports. This keeps the fixture out of the product auth package and avoids a second tenant/role resolver. The harness is a local transport replacement, not a new authorization policy.

The server replacement returns one of exactly three hard-coded synthetic Clerk-shaped identities: platform admin, tenant A owner, tenant B owner. Its `auth()` and `currentUser()` return synthetic `user_*`/`org_*` IDs, org role and public metadata in the shapes expected by `packages/auth/src/auth.ts` and `session.ts`. The isolated worker and both app children receive only the same fixed, visibly invalid Clerk schema placeholders because shared raw environment validation requires nonempty `CLERK_SECRET_KEY` and `CLERK_PUBLISHABLE_KEY` on health and worker paths. The children retain the loopback-only egress preload, and fixture aliases prevent Clerk SDK calls. No real Clerk key is read or supplied. The existing `resolveSession`, role mapping, `createTRPCContext`, `requireTenant` and admin procedures run unchanged. The local proof exercises those application authorization layers, not live Clerk token verification or the identity-binding validator. No route or client can supply arbitrary user, organization or role fields. Identity selection is a fixed enum in a local sign-in page; sign-out clears it. The cookie is `HttpOnly`, `SameSite=Strict`, host-only and task-scoped, signed with a fresh ephemeral local HMAC secret so an injected selector is rejected. The dashboard middleware and server components verify the same cookie. Cookies are not port-scoped, so both the web middleware and web server aliases intentionally return anonymous identity on port 56345 even if the browser sends the dashboard cookie there. The web tRPC gateway must reject protected procedures in that state. The dashboard's existing development-only visual-fixture layout path is used to render without a Clerk publishable key; it does not establish a session. Fixture auth must not support the Clerk backend management API; routes that need it fail closed.

The alias is installed only by Next's development webpack resolver, not as a source-level branch in `packages/auth`. Inventory direct and transitive Clerk imports first; because the dashboard uses direct Clerk imports and `@pathfinder/auth/server`, resolution must be verified through both paths and the middleware's edge bundle. The local fixture UI exports only the Clerk surfaces needed for these journeys (provider, sign-in/out, user and organization hooks); an unsupported API throws and cannot fall through to the real SDK. The server `auth()` obtains the signed selector from Next request cookies/headers in RSC, route handlers and tRPC, while `clerkMiddleware` reads the same selector from its `NextRequest`; both run the same guard. The sign-in page selects the identity through a local, POST-only endpoint with an exact enum, no arbitrary redirect URL, and a response that cannot set a cookie unless all guards pass. The API must be safe against CSRF even on loopback: require same-origin `Origin`, reject missing/foreign origin, and do not expose CORS.

### Refusal conditions

The guest web app also returns 404 for its local sign-in, sign-up and sign-out routes, including POST, so it never presents the dashboard fixture selector.

The harness is enabled only if **all** of these are true on every fixture request: `TORCHIKO_LOCAL_FIXTURE_AUTH === '1'`; `NODE_ENV === 'development'`; request host is exactly `127.0.0.1`, `localhost` or `[::1]` with the expected lane-C port; no environment variable name starts with `RAILWAY_` or `VERCEL`; and the HTTP listener is bound to loopback. Parse the host as a URL authority and reject userinfo, alternate numeric loopback spellings, forwarded-host overrides and ports outside the map. The guard is shared by middleware, sign-in/out endpoints and server alias. A missing/invalid condition denies fixture identity rather than falling back to an arbitrary user or real Clerk. The cookie is an intentional local test credential only for the disposable stack; a forged or tampered cookie is rejected. At startup the launcher checks socket ownership/bind addresses for both Next processes and stub. The exact `next dev --hostname 127.0.0.1 --port` invocation and an installed egress-guard sentinel are checked during config evaluation, so a direct fixture-flagged `0.0.0.0` launch or a forged `NODE_OPTIONS` string fails before the alias is installed. Acceptance includes a request against a non-loopback local interface with a forged localhost Host; it must fail to connect. Reverse proxies and LAN exposure are prohibited.

At config evaluation, `next build` must throw if the fixture flag is set, regardless of `NODE_ENV`. The alias is absent from a normal production build. Build both apps into fresh isolated dist directories under the machine workspace, then scan browser, server, edge, middleware and standalone/traced JavaScript, JSON manifests and source maps, for shim paths and a unique fixture-auth marker. Tests cover flag absent, every forbidden host, production mode, every `RAILWAY_*` and `VERCEL*` name, forged/tampered selector, cross-origin POST and build refusal in both apps. The production build takes the shared build lock. CI must never supply real Clerk keys; the launcher rejects any inherited Clerk key or hosted service credential rather than reading its value.

### Threat notes

- A fake `Host` header sent through a remotely bound listener would defeat a host-only gate. The launcher binds both Next servers and the provider stub to `127.0.0.1`, verifies the actual socket bind, and the request guard checks the host/port too. Do not add LAN exposure or a reverse proxy to this harness.
- A cookie switch grants admin rights within the **disposable local database** by design. It must not point at any hosted database. The launcher verifies exact disposable database name, loopback URLs, no Railway/Vercel environment, and synthetic identifiers before process start; a failure aborts startup.
- Browser and server code paths may resolve aliases differently. Acceptance includes a real browser sign-in through middleware, server-rendered layout, direct `@pathfinder/auth/server` call and tRPC request for each identity, plus tenant B denial of tenant A records. Unit mocks alone do not prove this.
- The existing `TORCHIKO_VISUAL_FIXTURES_ENABLED` path is separate, page-only and does not establish a session. Packet 14 must not treat it as authenticated proof.
- The launcher starts children with a minimal allowlisted environment, never inherited credentials. It sets only exact loopback database, Redis, storage and model-provider endpoints. A Node preload rejects non-loopback DNS/socket/HTTP/fetch destinations in each host process; dependency containers use an internal Compose network; the host-facing fixed-route port proxy uses a published bridge because Docker Desktop did not forward ports from an internal network and denied route removal. Its process forwards only to five named dependencies, but its container retains a raw outbound route. Playwright aborts non-loopback browser requests. The acceptance probe denies a TEST-NET-3 request before socket creation and audits established sockets of the attributed host processes; this is a point-in-time host proof, not a hard container egress block. No real venue data enters this stack. The three venues and tenants are invented and marked synthetic in seed source and logs.

## Stack and ports

The one-command Node launcher owns only a Compose project named with `nC-` and task-owned state under `C:/Users/tomsc/MachineWorkspaces/torchiko/20260928-local-full-stack/`. It does not call the shared `local-staging.ps1` or stop its containers. The exact loopback map is: Postgres 56340, Redis 56341, MinIO API 56342, MinIO console 56343, provider stub 56344, web 56345, dashboard 56346. M5's authenticated upload verification needs the existing ClamAV worker's scanner dependency. The isolated Compose stack includes a pinned ClamAV container on loopback port 56347, keeps its update traffic blocked by the internal network, and enables only the intake verification worker. This is Sol's design amendment for the local upload proof, not a connection to an external scanner. Every container/network name is prefixed `nC-`. `local:up` runs health waits, disposable migrations, synthetic seed, then stub, workers, web and dashboard with per-process logs and a state file. `local:down` stops only attributed lane-C processes/containers and preserves data. `local:reset` removes only this lane's disposable database/storage after a resolved-path ownership check and recreates it. `local:status` reports the same attributed identities and health. Start/stop are idempotent and failure paths stop only processes this launcher started.

The provider stub implements the current R1.1 client wire shapes: Responses streaming SSE (`response.output_text.delta` and terminal usage/status), non-stream Responses JSON, and embeddings in the SDK-requested base64 wire format that decodes into 1536 floats. The installed OpenAI SDK reads `OPENAI_BASE_URL`; the launcher sets it to the exact loopback stub URL and supplies only a literal synthetic API token. Local model selection uses the OpenAI-backed guest-chat Luna entry; Anthropic and DeepSeek keys are absent. Chat Completions is supported only for the local media path if that path is exercised. The web's `/api/chat-stream` retains its separate NDJSON browser protocol. Stub timing controls set first-token delay and token cadence. Unknown paths/models fail closed. The seed has three invented venues (science museum, small collection museum, nature centre), each with knowledge, appearance, QR and guide slug. Tenant A owns the first two; tenant B owns the third. No fixture copies a production venue.

Next's generated development output stays under ignored app-local directories inside the MachineWorkspaces checkout so its compiled modules resolve the installed React and Next packages. The installed Next 15 development router uses `localhost` in fixture sign-in redirects even when the TCP listener is bound only to `127.0.0.1`; the browser journey uses `localhost:56346` for dashboard navigation and `localhost:56345` for the same-host, cross-port cookie denial check. Both resolve to the fixed loopback listener. The public guide and its saved link use `127.0.0.1:56345`.
