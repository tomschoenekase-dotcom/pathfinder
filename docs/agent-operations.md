## CRM no-send development route

The existing `callProspectTool` bridge in `packages/api/src/agent-bridge/registry.ts` routes to `createProspectAgentRegistry` in `packages/api/src/prospect-agent/registry.ts`. Its exact contracts are in `tool-contracts.json`. A verified run needs the relevant frozen scope and capabilities; source declarations alone do not establish a live credential. `torchiko.prospects.search` finds a prospect, `get_intelligence` returns its source evidence, and `list_campaign_members` finds a campaign member. The `save_outreach_draft` tool persists a versioned candidate with agent and prompt lineage for human review. It has no approve, queue, or send capability.

For bounded research already queued by a platform administrator, the same registry exposes `claim_research_job`, `complete_research_job`, and `release_research_job` under the separate `prospects.research` capability. The queue owner in `packages/db/src/helpers/prospect-research-job-actions.ts` requires a human platform administrator to add prospect IDs; an agent cannot infer queue authority from its research capability. Check the selected prospect's existing evidence first, then use a queued job only when missing or stale facts materially affect the current draft. These tools record a job outcome and attempt lineage; they do not establish that an external research provider is connected or that new facts were saved to the prospect. Read those facts back through `get_intelligence` before citing them.

This tool **saves** copy; it does not generate an email. Its caller-provided evidence references do not by themselves verify venue facts. `copySources` resolves eligible company knowledge revisions for a separate review-only copy handoff. Inspect the current source and approval records before treating any Write Like Tom style or Approved Language candidate as accepted. Keep product claims, venue evidence, style, accepted phrasing, sales guidance, and the current task separately attributed. For provider-dark proof, run the focused `packages/api/src/prospect-agent/registry.test.ts`, `copy-assistant.test.ts`, and `packages/db/src/helpers/prospect-outreach-actions.test.ts`; the disposable database integration tests require their explicit safe target and opt-in.

## Action boundaries

The agent may inspect code, create isolated branches, make scoped reversible changes, run provider-dark tests, and leave handoffs. CRM write operations must pass the authenticated owner interface and its review states. Research and drafting use a single selected task, not a bulk enrichment prerequisite. Customer contact, real email sends, production promotion, live provider use, data imports, migrations, deletion, and purchases require their separate owner authority and readback. Preserve existing releases and rollback paths. Do not inspect or copy raw credentials.

## Handoff minimum

Record `task`, `owner`, `repository/worktree`, `base and result commit`, `changed paths`, `status`, `validation with exact command/result`, `unresolved issues`, `artifact links`, and `next safe action` in the existing task or AI-OS run. Use the current project's exact handoff writer and vault staging pointer where applicable. A result is complete only when the written artifact is read back and its relevant tests or workflow checks pass.
