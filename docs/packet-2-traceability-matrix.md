## Status key

- `implemented-foundation`: the cited, bounded local foundation exists and has focused evidence. It
  does not mean every outcome in the packet section is complete.
- `partial`: a material slice exists, but one or more packet outcomes remain unimplemented.
- `owner-blocked`: the next material step needs an owner, legal, security, commercial, or incident
  authorization that the worktree cannot supply.
- `packet-deferred`: Packet 2 explicitly defers the feature or requires evidence before it is built.
- `local-verified`: cited static/unit/component evidence exists. This is not staging or production
  evidence.
- `live-unverified`: runtime, browser, migration, provider, restore, or production evidence is absent
  or prohibited. This label must not be upgraded from local tests alone.
- `not-applicable`: the section is an instruction or intentionally deferred decision with no live
  behavior to verify now.

## Continuation evidence that must not be overstated

- Operational-update create, update, schedule and deactivate are canonical HUMAN manager/owner
  actions with exact scope, locks, CAS, capacity validation and strict transactional audit. Their
  lifecycle preview is local evidence, not proof of a running scheduler or live expiry behavior.
- The neutral intake DB service is shared by tenant and admin adapters and preserves exact scope,
  consent/privacy evidence, append-only events and existing-`DRAFT` lineage. It does not create,
  approve, apply or publish a package, and its migration remains unapplied.
- Support→DRAFT VenuePackage linkage is locally verified through unapplied migration
  `packages/db/prisma/migrations/20260811220000_add_support_package_handoffs/migration.sql`.
  It is exact tenant/venue/request/package scope, append-only, HUMAN-operator attributed, version-CAS
  guarded, and limited to an existing `DRAFT`. It makes zero package lifecycle writes.
- Support transitions are locally verified against an explicit closed graph: `OPEN` may move through
  waiting/review/cancel paths and patch/validation/approval/applying states to `COMPLETED`. They require
  a HUMAN `OPERATOR`, exact tenant/venue scope, expected version/current-status CAS, transactional
  append-only support event and strict platform audit. They have zero package lifecycle execution side
  effects. `VALIDATING` includes validation/evaluation review because the enum has no distinct
  evaluation state.
- Tenant Support reads and replies now require the immutable requester or an unrevoked explicit
  participant with active membership. `STAFF`, `MANAGER` and `OWNER` use the same predicate; role
  alone grants nothing. Requester-only replay-safe grant/revoke actions and safe current-user
  projections are locally verified. Only the requester can open the bounded, repeatable-read
  candidate roster and grant/revoke active members; participants cannot enumerate or manage it.
  Durable produced versions/timestamps keep ambiguous replay truthful after later activity or
  membership changes. Client-visible version/activity remains separate from global/internal history,
  every attachment remains uploader-owned, and platform-admin Support stays separate. Migrations
  `20260812000500` and `20260812001100` are unapplied, so this is not live evidence.
- The dedicated manual Support loop atomically records an operator information prompt and bounded
  checklist (`OPEN`/`IN_REVIEW` → `WAITING_FOR_CLIENT`), an authorized requester/active-participant
  response with uploader-owned trusted attachments (`WAITING_FOR_CLIENT` → `IN_REVIEW`), or an
  operator completion message for an empty-checklist `OPEN`/`IN_REVIEW` request. Global/client
  versions, immutable message evidence, request events and strict audit move together; replay uses
  durable produced-version evidence. No action creates/applies a package or triggers execution.
  Migration `20260812000900_add_support_message_request_version` is unapplied and has no live proof.
- Terminal Support→AgentRun association is immutable evidence for an exact existing request audit
  version and exact same-venue terminal run. The canonical status/completion snapshot is checked at
  insert; UUID/hash replay and audit perform no Support version/status, run, approval, action,
  package, provider or execution mutation. Migration `20260812001000` also preflights and guards the
  exact run→approval request→APPROVED decision→action chain. It has no backfill, remains unapplied,
  and deliberately exposes no reverse run backlink.
- Client onboarding task evidence reuses that exact ACL and is bounded before rendering. Tenant
  staff-review responses are a positive safe DTO; confidence, discrepancies, readiness, timelines,
  hashes and internal evidence remain on the separately authorized admin projection.
- Generation workers renew exact live leases around provider waits and pass an `AbortSignal` into
  the gateway. Ownership loss conservatively settles dispatched cost as ambiguous, prevents
  redispatch and fences stale terminal writes; these are fake-timer/unit contracts, not live provider
  evidence.

  evidence. HUMAN platform-admin conclusions require an exact `COMPLETED` run and replay-safe
  revision CAS with sanitized audit. Migration `20260812000600_evaluation_review_commands` is
  unapplied, and neither comparison nor conclusion is a package gate.
